// 01   What I was handed

A well-factored monolith, frozen in 2018

The solution is genuinely well-structured — a web app, a REST API, a React SPA, and shared Common/Data layers using Repository + Unit of Work, AutoMapper, the options pattern, and multiple DbContexts. The problem was never the architecture; it was that everything sat on a runtime that has been unsupported for years, with a handful of choices that quietly block any cloud move.

The blockers, before touching anything

  • Unbuildable baseline. Targets netcoreapp2.1, SDK pinned to 2.1.300 in global.json — not even installable on a current machine. The "green tests on 2.1" baseline was a fiction; the upgrade is the baseline.
  • No migration history. Only *ModelSnapshot.cs committed — zero migration classes. Azure SQL has nothing to apply. (Root cause turned out to be a .gitignore rule — see §03.)
  • Secrets & state tied to the box. JWT signing key is a symmetric secret in config; Data Protection uses the default local key ring (cookies break across instances/restarts); connection string hardcoded to LocalDB.
  • Runtime-OS branching. The DB provider was chosen by inspecting the OS (LocalDB / SQLite / InMemory) — fine for a tutorial, wrong for a reproducible cloud image.
  • Deprecated toolchain. Bower for client libs, Swashbuckle 1.0.0, xUnit 2.2, Travis CI, two different hosting models (one hand-built WebHostBuilder).

// 02   The cloud target

Replatform to managed PaaS — portable by design

A lift-and-shift to VMs would have carried every problem above into the cloud. A full rewrite to microservices/serverless wasn't warranted — the monolith is healthy. The right move is a replatform: modernize the runtime, push every host-bound dependency (secrets, keys, database identity) out to managed services, containerize, and let a managed platform run it.

I designed against Azure App Service for Containers, but deliberately chose services that have a clean 1:1 AWS equivalent, so the same design ports without rethinking. The only Azure-specific glue is the SDK names — the shapes are identical.

// 03   Code I recommend changing — and did

Six fronts, each with a reason

None of the cloud services matter until the code can use them. These are the concrete changes, grouped, each shown as before → after.

Runtime
Retarget all 10 projects and modernize hosting so the platform — not the OS — runs the app. netcoreapp2.1, two hosting models, UseMvc, IHostingEnvironment → net10.0, one generic host (keeping Startup so the integration tests survive), endpoint routing, Swashbuckle 7 OpenApiInfo.
Data
One provider, real migration history, resilient connections. OS-branched LocalDB/SQLite/InMemory, no migration classes → single SQL Server provider with EnableRetryOnFailure; regenerated InitialCreate + InitialIdentity; idempotent deploy scripts.
Security
Nothing secret in source; nothing reached with a password. JWT key + SendGrid/Twilio/OAuth in config; SQL via connection-string creds → Key Vault layered as a config source via DefaultAzureCredential (Managed Identity); SQL via Authentication=Active Directory Default.
Resilience
Survive scale-out and sit correctly behind an edge. local Data Protection key ring; HTTPS a config toggle; no forwarded headers → DP keys persisted to Blob + wrapped by a Key Vault key; HSTS/HTTPS always-on outside Dev; forwarded headers for Front Door.
Observability
Make the platform able to tell if the app is alive and healthy. no health endpoints, no telemetry → /health/live + /health/ready (with a DB check), Application Insights wired on a connection string.
Front-end & tests
Drop dead tooling; test against the real engine. Bower; EF InMemory integration tests; AutoMapper 12 (CVE); react-scripts 3 (EOL) → LibMan + pinned Node; Testcontainers (real SQL Server); AutoMapper 15.1.1; react-scripts 5.

What "based on the real exercise" actually surfaced

The plan looked tidy; reality had teeth. Three findings worth keeping:

  • The missing migrations were a .gitignore bug. The repo wasn't missing migrations by accident — a */Migrations/* rule was silently ignoring every migration class. Deleting stale snapshots and removing the rule produced a real history.
  • The AutoMapper bump was a security fix, not cosmetics. 12.0.1 carries a high-severity DoS advisory (GHSA-rvv3-g6hj-g44x); only 15.1.1 clears it, which then required an ILoggerFactory on MapperConfiguration.
  • CRA's upgrade fought back. react-scripts 5 on a clean install exposed a real peer conflict (redux-thunk needing redux@4); --legacy-peer-deps had only hidden it behind a broken ajv tree. Aligning the deps let it compile.

// 04   Architecture

Target topology on Azure

Public traffic enters through Front Door + WAF. Two container apps (Web + API) share one Linux plan, each with a staging slot for blue-green. Every backing service is reached by the app's system-assigned Managed Identity — the dashed lines below carry an identity token, never a password.

// 05   Build pipeline

One commit to production, with a gate in the middle

Travis is retired in favor of an Azure DevOps multi-stage YAML pipeline (azure-pipelines.yml). Source stays on GitHub; only the pipeline moves to Azure DevOps. Azure is reached through an ARM service connection using Workload Identity Federation — OIDC, so there are no stored cloud secrets.
